# Firestore Cost-Optimization Standard (파이어스토어 DB 절약 표준 스킬)

Cloud Firestore는 읽기(Read), 쓰기(Write), 삭제(Delete) 횟수 기반으로 과금되므로, 트래픽이 폭증해도 요금 폭탄을 방지하고 빠른 반응 속도를 보장하기 위해 다음 최적화 규칙을 필수로 준수합니다.

---

## 1. 읽기 비용 제로화 원칙: Cache-First 전략 (가장 중요)
- **로컬 스토리지 / 메모리 캐싱 우선**:
  - 변경이 드문 기준 데이터(지하철역 출구 정보, 무장애 시설, 기본 추천 코스 등)는 절대 Firestore를 매번 조회하지 않고, 로컬 정적 데이터(`src/data.ts`)나 `recommendations-db.json`을 기본으로 사용합니다.
  - 클라이언트에서 Firestore를 읽을 때는 항상 `localStorage` 또는 `sessionStorage`에 타임스탬프와 함께 캐싱하고, TTL(예: 12~24시간)이 유효하면 Firestore 네트워크 호출을 완전히 건너뜁니다.
- **버전/해시 기반 스마트 동기화**:
  - 컬렉션 전체를 다시 읽는 대신, 최신 업데이트 시각(`lastUpdatedAt`) 1건만 먼저 단일 `getDoc`으로 확인하여 변경이 있을 때만 본문 데이터를 갱신합니다.

---

## 2. 쿼리 최적화 및 읽기 횟수 최소화
- **실시간 리스너(`onSnapshot`) 남용 절대 금지**:
  - 실시간 채팅이나 주식 호가창이 아닌 여행 정보/추천 글에는 `onSnapshot` 대신 **1회성 조회(`getDocs`)**를 사용합니다. 실시간 리스너는 문서가 바뀔 때마다 모든 연결 클라이언트에 대량의 읽기 과금을 유발합니다.
- **항상 `limit()` 제약 적용**:
  - 컬렉션 쿼리 시 반드시 `limit(10)` 또는 `limit(20)`을 걸어두어 한 번의 조회로 수백~수천 건이 무단으로 읽히지 않도록 엄격히 방어합니다.
- **문서 역정규화 (Denormalization)**:
  - 1:N 관계에서 N이 크지 않은 데이터(예: 역별 출구 목록, 코스별 방문지 배열 등)는 별도의 서브컬렉션으로 쪼개지 않고, 부모 문서 하나에 `Array`나 `Map`으로 통합하여 **1회의 Document Read로 전체를 취득**합니다.

---

## 3. 쓰기 비용 절감 및 일괄 처리
- **클라이언트 측 디바운싱(Debounce) & 스로틀링(Throttle)**:
  - 추천수 증가(좋아요), 검색 로그, 조회수 등 빈번한 사용자 인터랙션은 즉각적인 Firestore Write를 방지하고, 클라이언트에서 500ms~1초 디바운스 후 전송합니다.
- **낙관적 업데이트 (Optimistic UI)**:
  - 추천수(`upvotes`) 클릭 시 사용자 화면에는 즉시 `+1`을 반영하고, Firestore 저장은 백그라운드에서 조용히 처리하거나 로컬 스토리지(`busan_traveler_upvotes`)에 먼저 기록합니다.
- **배치 쓰기 (`writeBatch`)**:
  - 여러 문서를 업데이트하거나 생성할 때는 개별 호출 대신 `writeBatch`를 사용하여 네트워크 왕복 비용을 최소화합니다.

---

## 4. 서버 측 프록시 캐시 (`server.ts`)
- 클라이언트들이 Firebase에 각자 직접 쿼리하는 대신, 백엔드 Express 서버(`server.ts`)가 Firestore 데이터를 인메모리에 보관하고 클라이언트에는 서버 캐시 응답을 반환하여, 수만 명의 사용자가 접속해도 Firestore 읽기 비용을 극적으로 낮춥니다.
